# SpecsIntact Modern - Revised Software Development Plan

**Version:** 3.0 (Post-Human-Testing Edition)
**Date:** March 2026
**Context:** This plan incorporates every lesson learned from the 47-phase build of SpecsIntact Modern v2.0.0 AND the 23-bug human testing session that followed. It describes how the same application - with identical features and the same final architecture - would be built from scratch in 29 phases instead of 47, eliminating all rework, retrofit, and remediation phases while baking in the contentEditable safety patterns discovered during testing.

---

## 1. Executive Summary

SpecsIntact Modern is a browser-based and desktop WYSIWYG editor for Unified Facilities Guide Specifications (UFGS) `.sec` files. It replaces the legacy Windows-only SpecsIntact application used by NAVFAC, USACE, and AFCEC.

This plan delivers a distributable application - both as a hosted web app and an installable Windows desktop app - that a specification engineer can install without developer tools and use daily. The plan is organized into 29 phases across 5 tiers, estimated at 15-20 working sessions.

### What this plan changes vs. the original

| Original Plan | This Plan | Why |
|---------------|-----------|-----|
| Build system introduced at Phase 31 (after 30 phases of features) | Build system is Phase 1 | Eliminates the ESM migration (Phase 32) and prevents all require/module.exports debt |
| app.jsx grew to 2,245 lines, then decomposed in Phase 34 | Module structure defined in Phase 1, features added to correct modules | Eliminates the decomposition rework phase entirely |
| Bundled reference data added at Phase 38 | Bundled at Phase 12 (right after Reference Wizard) | Removes manual UMRL/UMSL loading from 25+ development sessions |
| Playwright E2E tests added at Phase 39 | E2E suite introduced at Phase 21, grows with every subsequent phase | Catches rendering bugs that source-scanning tests miss |
| Electron shell created in Phase 41, wired in Phase 43 | Electron scaffolded in Phase 1, wired incrementally | No separate "Electron integration" phase needed |
| UX review at Phase 42 only | UX reviews at Phase 15 and Phase 25 | Catches usability gaps while they are cheap to fix |
| 47 phases total (including 5 rework + 5 remediation) | 29 phases (zero rework, zero remediation) | Same features, 40% fewer phases |
| INI parser ships as runtime module | INI parser is build-time only, produces static JSON | Simpler bundle, no runtime INI code |
| Three separate file-I/O implementations | One unified file-I/O abstraction from the start | encoding.js handles all environments cleanly |
| Three development plan documents | One living document | Easier to search and maintain |
| No contentEditable safety rules | execCommand guard pattern, non-editable island pattern, and effectiveText() mandated from Phase 5 | Prevents the entire class of 8 corruption bugs found in testing |
| Keyboard shortcuts used raw e.key | All shortcuts normalize with toLowerCase() | CapsLock-safe from day one |

## 2. Scope and Objectives

### Primary objective

Deliver a standalone, distributable application that a specification engineer can install on Windows without using a terminal and use daily to edit UFGS `.sec` files, replacing legacy SpecsIntact for the core editing workflow.

### In scope

- Parse, render, edit, validate, and save `.sec` files with byte-identical round-trip fidelity
- WYSIWYG editing via contentEditable with no SGML tag exposure to the user
- Structural editing (PART/Article/Subpart promote, demote, reorder)
- Tailoring system (option visibility, filtering, removal)
- Reference management (UMRL search, manual entry, reconciliation)
- Submittal management (UMSL search, register, reconciliation)
- Revision tracking (ADD/DEL/CHG with accept/reject)
- Table editing (grid model, cell/row/col operations, merge)
- Validation engine (7 checks with click-to-navigate)
- Print/publish pipeline (HTML output with reconciliation)
- Job and Master management
- QA reports (brackets, test requirements, references, submittals, SRFs, tailoring)
- Bundled UMRL (4,973 references) and UMSL (13,203 submittals)
- IndexedDB persistence for preferences and cached data
- File System Access API save-in-place (Chrome/Edge)
- Electron desktop wrapper with native dialogs and installer
- Browser spell check with preference toggle
- First-run onboarding overlay
- Playwright E2E test suite

### Out of scope (deferred)

| Item | Rationale |
|------|-----------|
| Multi-user collaboration | Requires server architecture not needed for primary use case |
| Plugin/extension system | Premature; core features not yet in production use |
| Word/PDF import | Different problem domain; low priority |
| Online UMRL/UMSL updates | Requires network integration; manual loading works as override |
| SpecsIntact project database (.sip) | Format not fully documented |
| Code signing for Windows installer | Requires certificate purchase; deferred to post-release |
| Auto-update mechanism | Requires update server; manual re-install is acceptable initially |

## 3. Architecture

### Target file structure (established in Phase 1)

```
secwriter/
  package.json                   type:module, Vite + React + Electron deps
  vite.config.js                 React plugin, relative base, chunk splitting
  index.html                     Vite SPA entry
  playwright.config.js           E2E test config
  DEPLOY.md                      Deployment guide
  README.md                      Project documentation

  src/
    main.jsx                     React entry (renders App into #root)
    app.jsx                      App shell: tabs, state, file I/O routing
    theme.js                     Colors, constants, TAG_LABELS, dialog styles
    sec-dom.js                   Unified SecNode class (parser + editor)
    encoding.js                  Windows-1252 codec, file I/O abstraction (browser + Electron)
    parser-browser.js            Browser-side tokenizer, tree builder, serializer
    sec-helpers.js               Reference, submittal, validation business logic
    persistence.js               IndexedDB storage (prefs, cached data, recent files)
    sec-parser.js                Node.js XML parser (round-trip fidelity)
    structural-ops.js            SPT promote/demote/reorder, OLG/OLI operations
    tailoring.js                 TAI option management
    references.js                UMRL database, reconciliation
    submittals.js                UMSL database, register generation
    revisions.js                 ADD/DEL/CHG tracking
    tables.js                    Table grid model, cell operations
    validation.js                7-check validation engine
    publish.js                   Print/publish pipeline
    job-master.js                Job and Master management
    qa-reports.js                QA report generation
    section-config.json          Pre-built validation rules (from INI, build-time only)

  electron/
    main.cjs                     Electron main process (window, menus, IPC)
    preload.cjs                  Context bridge (electronAPI)
    icon.png                     Application icon (256x256)

  public/
    data/
      umrl.ref                   Bundled reference database
      umsl.lst                   Bundled submittal database
      section-config.json        Bundled validation config

  test/                          Node.js test suites
  e2e/                           Playwright browser tests
    fixtures/                    Test .SEC files
  docs/                          Development plan, reviews
  tools/
    build-config.js              INI parser (build-time only, not bundled)
```

### Key architectural decisions (locked from Phase 1)

1. Custom XML lexer for byte-identical round-trip fidelity (not DOMParser)
2. Unified SecNode class in sec-dom.js (shared by parser and editor)
3. Vite + ES modules throughout (no CommonJS, no migration needed)
4. Module-per-concern structure (no monolith accumulation)
5. Unified file I/O abstraction in encoding.js (Electron > FSAPI > download)
6. Browser File API as the primary open mechanism, with Electron native dialogs as enhancement
7. Undo via XML snapshot serialization (80-level stack)
8. INI-driven configuration via build-time generation of section-config.json
9. Windows-1252 re-encoding on save
10. contentEditable with reconstructFromDOM bridge
11. IndexedDB for all client-side persistence
12. Electron shell scaffolded from Phase 1 (wired incrementally, built last)
13. contentEditable safety rules: all inline semantic tags (RID, SUB, SRF, ADD, DEL, HLS, TAI) render as `contentEditable={false}` islands in edit mode; every `document.execCommand()` call is guarded against non-editable regions; `effectiveText()` used for all text extraction from nodes that may contain revision markup; all toolbar/popup buttons use `onMouseDown={preventDefault}` to preserve selection; all keyboard handlers normalize `e.key` with `toLowerCase()` for CapsLock safety; scroll position is preserved across React re-renders via `scrollPosRef`

## 8. Testing Strategy

### Principles

1. Every phase produces a test suite that runs via `node test/[name]-tests.js`.
2. Full regression (all suites, 0 failures) is required before advancing to the next phase.
3. Playwright E2E tests are introduced at Phase 21 and grow with each subsequent phase.
4. Source-scanning tests (grepping code for patterns) are used sparingly - only for structural invariants like round-trip fidelity. Behavioral assertions belong in E2E tests.
5. Round-trip fidelity (byte-identical parse-serialize) is tested on every corpus file in the parser test suite. This is a hard gate that never relaxes.

## 9. Session Strategy

### Session structure

Each session follows this sequence:

1. State the phase number and goal.
2. Provide the actual source files being modified (not verbal descriptions).
3. Implement the phase deliverables.
4. Run the new test suite (must pass).
5. Run full regression (all existing suites, 0 failures).
6. Run Vite build (must succeed, bundle size within budget).
7. Deploy modified files to the output directory.
8. Update run-tests.sh and README with new suite and counts.

### Context management

At the start of each session, provide:
- The phase number and goal from this plan.
- The current file manifest (which files exist, line counts).
- Any files being modified (full content, not descriptions).
- The previous session's test count and any known issues.

For complex phases (5, 8, 9, 14), provide only the files being modified plus their direct imports. Do not load files that will not change.

### Rollback protocol

If a phase introduces regressions that cannot be fixed within the session:
1. Revert to the pre-phase working directory.
2. Identify the root cause in the session notes.
3. Re-attempt in the next session with a revised approach.

This has never been needed in 47 phases, but the protocol exists.

## 10. Key Decisions Explained

### Why Vite (not Webpack, not Parcel)

Vite supports React JSX out of the box, has zero-config defaults, provides sub-second hot reload, and produces optimized production bundles with chunk splitting. The project uses simple patterns (no decorators, no complex imports) that work with Vite's defaults.

### Why Electron (not Tauri, not PWA)

The target users are on government Windows machines where PWA installation is often blocked by policy. Tauri requires Rust toolchain installation. Electron produces a standard Windows installer that IT teams understand. The trade-off (larger binary size) is acceptable for an intranet-distributed application.

### Why custom XML parser (not DOMParser)

Browser DOMParser normalizes whitespace, reorders attributes, and converts encodings - all of which break round-trip fidelity. The custom lexer preserves exact byte sequences for the 46 corpus files tested. This is a non-negotiable requirement for SpecsIntact interoperability.

### Why contentEditable (not ProseMirror, not Slate)

The document model is the SEC DOM, not a ProseMirror schema. contentEditable with a reconstructFromDOM bridge lets us project from the SEC DOM to HTML and reconstruct back on blur. This avoids the complexity of translating SEC's 53 tags into a ProseMirror schema while maintaining the exact same behavior the user sees in legacy SpecsIntact. The trade-off (contentEditable quirks) is manageable because the edit regions are tightly scoped (individual paragraphs, not the whole document).

**Critical safety rules for contentEditable (learned from testing):**

- All inline semantic tags (RID, SUB, SRF, ADD, DEL, HLS, TAI) must render as `contentEditable={false}` spans with `data-sec-uid` in edit mode. This prevents `document.execCommand` from corrupting structured content.
- Every `document.execCommand()` call must be guarded: walk up from `sel.anchorNode` checking `contentEditable`; if `false` is hit before `true`, skip the command or route the operation through the SEC DOM via `mutate()`.
- Every toolbar/popup button that depends on an active selection must use `onMouseDown={e=>e.preventDefault()}` to prevent focus loss from the contentEditable region.
- Text extraction from SEC nodes that may contain revision markup (ADD/DEL) must use `effectiveText()` (which skips DEL children), never `nText()` or `.text()`.
- The document container's React `key` includes a version counter that changes on every edit. Scroll position must be saved before and restored after re-renders using a ref and `requestAnimationFrame`.
- The undo stack must push the post-edit state (call `fn()` then `snap()`), not the pre-edit state.

### Why INI parser at build-time only

section.ini is a SpecsIntact configuration file that defines margins, colors, entities, and nesting rules. It changes rarely (only when SpecsIntact is updated). Parsing it at runtime adds complexity (runtime INI parser in the bundle) for no user benefit. Instead, a build-time script reads section.ini and produces section-config.json, which is bundled as a static asset.

### Why one file-I/O abstraction

File I/O has three environments: Electron (Node.js fs via IPC), Chrome/Edge (File System Access API), and fallback (Blob download). Each environment has different APIs for open, save, and save-as. Rather than branching in app.jsx, a single module (encoding.js) exports `openFiles()`, `performSave()`, and `saveAs()` that internally detect the environment and dispatch. app.jsx never needs to know which environment it is running in.

## 11. Risk Register

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| contentEditable browser quirks (paste formatting, spell check DOM changes) | Medium | Medium | Scope contentEditable to individual paragraphs. Strip HTML on paste. Spell check attribute controlled by preference. reconstructFromDOM handles unknown spans by unwrapping. |
| `document.execCommand` corruption inside non-editable regions | High | High | Guard every execCommand call site. Walk up from selection anchor checking contentEditable boundaries. If `false` is hit before `true`, skip the command or route through SEC DOM. This was the single largest bug class found in testing (8 of 23 bugs). |
| Revision markup (ADD/DEL) in headings breaks text extraction | High | Medium | Use `effectiveText()` (skips DEL children) for all text reads from SEC nodes. Never use `nText()` or `.text()` on TTL, SUB, or other nodes that could contain revision markup. |
| React key-based re-render resets scroll/focus | Medium | High | Never include a mutation counter in a React `key` without scroll restoration. Use `scrollPosRef` + `requestAnimationFrame` to restore position after structural re-renders. |
| Round-trip fidelity regression | Low | Critical | Parser test suite runs on every corpus file. Any byte-level difference is a hard failure. Never bypass this gate. |
| Electron packaging complexity | Medium | Low | Minimal wrapper: file dialogs and window chrome only. No native modules. Unsigned initial build (SmartScreen workaround documented). Custom `app://` protocol required for Vite ES module loading. |
| Vite build breaks with new dependencies | Low | Low | Project uses only React, iconv-lite, and jsdom. No complex import chains. |
| Government network blocks npm install for end users | High | None | End users never run npm. They receive a pre-built .exe installer or access a hosted web URL. npm is developer-only. |
| UMRL/UMSL data becomes outdated | Medium | Low | Bundled data can be overridden by manual file loading. Updated data files can be swapped in public/data/ and rebuilt. |
| Browser spell check modifies DOM in unexpected ways | Low | Medium | Tested empirically in Phase 5. If problematic, disable on specific elements. Browser spell checkers typically use CSS pseudo-elements that do not persist in the DOM on blur. |
| Context loss during long Claude sessions | Medium | Medium | Provide file manifests. Work on one file at a time. Full regression after every phase catches regressions even when context is incomplete. |
| Keyboard shortcuts fail with CapsLock | Medium | Low | All handlers normalize `e.key` with `toLowerCase()`. Never compare raw `e.key` against lowercase letters. |

## Appendix A: Lessons Learned (from the original 47-phase build)

These lessons directly informed every decision in this plan.

| Lesson | How It Changed This Plan |
|--------|-------------------------|
| Retrofitting a build system across 14 modules and 33 test files was a full session of pure rework | Build system is Phase 1 |
| A 2,245-line monolith hit context limits and required a decomposition phase | Module structure defined in Phase 1 |
| Manually loading UMRL/UMSL every development session was friction that accumulated over 25+ phases | Bundled data at Phase 12, immediately after the features that need it |
| Source-scanning tests broke every time code was restructured, requiring repeated test fixes | Minimal source-scanning; behavioral tests via Playwright |
| The UX review at Phase 42 found five issues that would have been trivial to fix at Phase 15 | Two UX review checkpoints, not one |
| The Electron shell was created in Phase 41 but not wired to the renderer until Phase 43 | Electron scaffolded in Phase 1, wired incrementally |
| The INI parser was built as a runtime module but is only used at build time | Build-time only, excluded from bundle |
| Three separate file-I/O implementations (browser download, FSAPI, Electron) evolved across four phases | One abstraction from Phase 4 |
| Round-trip fidelity is the single most important technical requirement and must never be compromised | Parser test suite is a hard gate on every phase |
| Phased development with test-first validation works extremely well for AI-assisted development | Retained. One phase per session. Full regression before advancing. |
| Providing actual source files (not verbal descriptions) produces better results from Claude | Explicit in session strategy |
| document.execCommand corrupts content inside contentEditable={false} regions - 8 of 23 bugs were this class | Mandatory execCommand guard pattern from Phase 5 (see Appendix B, Pattern 10) |
| nText() and .text() on nodes with ADD/DEL revision markup concatenate both versions, breaking article finding | effectiveText() required from Phase 5 (see Appendix B, Pattern 5) |
| Keyboard shortcuts fail with CapsLock because e.key reports uppercase letters | All handlers normalize with toLowerCase() (see Appendix B, Pattern 3) |
| React key={...ver} causes full DOM destruction and scroll reset on every edit | scrollPosRef save/restore pattern required from Phase 5 (see Appendix B, Pattern 9) |
| Toolbar buttons steal focus from contentEditable, making formatting commands fail silently | onMouseDown={preventDefault} on all formatting buttons from Phase 5 (see Appendix B, Pattern 4) |
| Undo stack pushing pre-edit state makes redo appear to do nothing | snap() must be called after fn(), not before (see Appendix B, Pattern 12) |
| A proactive bug audit after testing caught 16 additional latent sites across 2 vulnerability patterns | Proactive audit added to Phase 28 release validation |

## Appendix B: Bug Pattern Catalog

These 15 patterns were extracted from the 23 bugs found during human testing of v2.0.0. Every pattern has been verified clean in the current codebase. This catalog should be used as a checklist during Phase 28 (Release Validation) and whenever new code is added.

| # | Pattern | Example Bug(s) | What To Check |
|---|---------|----------------|---------------|
| 1 | Temporal dead zone / declaration order | BUG-001, 002 | Every `useEffect`, callback, and event handler must only reference `const`/`let` variables declared above them in the file. |
| 2 | Private symbol leakage | BUG-003 | No module consumer should access internal `_variables` directly. Use exported getters/setters. |
| 3 | Keyboard event case sensitivity | BUG-006, 007 | All `e.key` comparisons for letter keys must normalize with `e.key.length===1 ? e.key.toLowerCase() : e.key`. |
| 4 | Focus loss from toolbar buttons | BUG-008 | Every button whose `onClick` depends on an active selection inside a contentEditable region must have `onMouseDown={e=>e.preventDefault()}`. |
| 5 | Revision markup text extraction | BUG-009, 011 | Every call to `nText()`, `.text()`, or `textContent` on a node that could contain ADD/DEL children must use `effectiveText()` instead. |
| 6 | Stale/divergent state objects | BUG-010 | Settings maintained in both standalone `useState` and a composite object must sync in both directions. |
| 7 | DOM hierarchy assumptions | BUG-017 | Functions scanning for elements must not assume they are direct children. Use recursive walkers when the spec allows nesting inside wrappers like TXT. |
| 8 | Missing/implicit imports | BUG-018 | No `React.*` references without imports. Check for any unimported symbols across all files. |
| 9 | React key-driven DOM destruction | BUG-021 | Any `key={...}` prop that includes a mutation counter must have scroll/focus restoration logic. |
| 10 | execCommand inside contentEditable=false | BUG-022, 023 | Every `document.execCommand()` call must guard against non-editable regions by walking up from the selection anchor. |
| 11 | Selection tracking via getSelection() | BUG-012 | Features tracking position across operations must use a persistent ref, not `window.getSelection()` which resets on DOM changes. |
| 12 | SEC DOM mutation without visual refresh | BUG-013 | Every code path that modifies SEC DOM nodes must trigger a React re-render afterward. Undo snap must capture post-edit state. |
| 13 | execCommand non-toggle behavior | BUG-014 | Formatting commands assumed to toggle (especially `hiliteColor`) need explicit "is already applied?" checks. |
| 14 | Scroll/UI timing vs React batching | BUG-016 | `scrollIntoView()`, `focus()`, and similar imperative DOM calls after state updates need `setTimeout` or `requestAnimationFrame`. |
| 15 | Append instead of sorted insert | BUG-015, 019 | Any function inserting into an ordered list must scan for the correct position, not append. |

Reference: Full bug details in `docs/bug-tracker.md`.
