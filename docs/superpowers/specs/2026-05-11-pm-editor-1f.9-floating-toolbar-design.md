# PM Editor 1f.9 — FloatingToolbar PM-Transaction Conversion (Design)

**Parent:** issue [#47](https://github.com/mttvnst-HA/secwriter/issues/47). Predecessor sub-PR: 1f.8 ([#65](https://github.com/mttvnst-HA/secwriter/pull/65), Track Changes del-popup).

## Goal

Convert `src/components/FloatingToolbar.jsx`'s six mark-application verbs from DOM mutation (`range.surroundContents` + read `blockEl.innerHTML` + `onBlockUpdate`) to PM transactions when the focused block is a mounted PM `EditorView`. Five verbs are converted; the comment button is the documented carve-out (issue [#64](https://github.com/mttvnst-HA/secwriter/issues/64) drops the `comment` mark in `prosemirrorToYXmlFragment`). Resolve the ~6 currently-failing toolbar E2E tests under the `chromium` project (PM mode); zero new failures under `chromium-legacy`.

## Architecture

### Three-branch handler in `FloatingToolbar.jsx`

Each of the five PM-converted verb handlers (`applyFormat`, `applyMark`, `applyRevision`, `handleInlineRevisionAction`, `changeCase`) gets a forking head:

```js
const blockId = selectionRef.current?.blockId;
const view = blockId ? getBlockView(blockId) : null;

if (view) {
  // PM path — read selection from PM state, dispatch transaction, flush.
  const { from, to } = view.state.selection;
  const tr = applyXxxTr(view.state, params);
  if (tr) {
    view.dispatch(tr);
    flushPendingUpdateById(blockId);   // synchronously fires onUpdate
    if (params.needsTcSnapshotRefresh && onRefreshTcSnapshot) {
      onRefreshTcSnapshot(blockId, pmFragmentToHtml(view.state.doc));
    }
  }
} else {
  // Legacy DOM path — existing code, unchanged.
}
setVisible(false);
```

- The PM branch reads `view.state.selection` directly. `selectionRef.current.range` (saved DOM Range) is only used in the legacy branch. `ySyncPlugin` keeps PM's selection mapped through remote ops via RelativePositions, so PM selection survives peer edits between click and dispatch.
- Comment button stays on the legacy DOM-mutation path unconditionally (no PM branch); the `<span class="mark-comment">` will be reverted by PM's DOMObserver, but the metadata still reaches `commentsState` via `onCommentCreate`. Visible highlight invisibility is the documented #64 limitation.

#### Critical PM semantics (load-bearing)

1. **Attr-discriminated mark detection.** `state.doc.rangeHasMark(from, to, type)` matches by `MarkType` only. For `inlineMark` (`kind` attr) and `revision` (`kind` + `authorId` attrs), the stock predicate spuriously reports "RID present" when only SRF is present, and `tr.removeMark(from, to, markType)` strips all attrs/kinds across the range. Use `rangeHasMarkWithAttrs` for detection and pass a **Mark instance** (not MarkType) to `tr.removeMark` so attrs-matching is honored.
2. **Multi-author revision safety.** `applyRevisionTr` with current identity `A`:
   - If the range contains *any* revision mark with `authorId !== A`: apply a fresh `(kind=K, authorId=A)` mark over the range. Do NOT toggle off the other user's mark.
   - If all revisions in range match `(kind=K, authorId=A)`: toggle off via `tr.removeMark(from, to, markInstance)` (Mark instance, not MarkType).
   - Otherwise (no matching revision in range): apply mark.
   - **Intentional behavior change vs. legacy.** Legacy `applyRevision` (`FloatingToolbar.jsx:230-234`) uses `closest('ins.mark-add')` without an author check — clicking Mark-as-Addition while standing inside *anyone's* `<ins>` strips their mark. That is a latent multi-user bug. The PM path declines to reproduce it. Pinned by U3c/U3d.
3. **Inline-resolve scope is per-mark instance, regardless of author.** When the cursor is inside `<ins data-author-id="B">`, clicking Accept in the toolbar resolves B's mark — that is the existing UX in legacy. Only the *apply* path is author-gated.
4. **Stored-marks cleanup.** `applyInlineRevisionResolveTr` returns a `tr` with `setStoredMarks([])` so the cursor at the resolve boundary does not inherit the just-removed mark for the next keystroke. Pinned by Vitest + an E2E typing-after-accept assertion.
5. **`inclusive: true` boundary.** The schema does NOT set `inclusive: false` on `revision` / `inlineMark` (PM defaults to inclusive). `findMarkRangeAt` accepts a cursor at the immediate right boundary of a mark as "inside the mark" and resolves it. A cursor *one position past* the boundary returns null. Both cases pinned by Vitest.
6. **Mark preservation in change-case.** `tr.replaceSelectionWith(state.schema.text(newText))` drops marks on the replaced range. Matches legacy `range.deleteContents()` behavior. Pinned by Vitest so a future mark-preservation enhancement doesn't silently change behavior.

### `flushPendingUpdate` — debounce closure

`PmEditableBlock.jsx:408-413` debounces `onUpdate(blockId, html)` 400ms after any local `dispatchTransaction`. Without flush:
- App's `blocks` ref carries pre-toolbar html for up to 400ms.
- `useCollabSession`'s publishBlocks effect emits stale entries (mitigated by the html-skip in `collab.js` `fb34a0a`, but TC snapshot text from `snapshotTextRef.current` and `compliance-ranges.js` offsets are read from React state).
- The next blur diff annotates against a stale snapshot text — TC inline marks land at wrong positions.

`flushPendingUpdate` (registered by PmEditableBlock):
```js
flushPendingUpdate: () => {
  if (onUpdateDebounceRef.current) {
    clearTimeout(onUpdateDebounceRef.current);
    onUpdateDebounceRef.current = null;
  }
  const view = viewRef.current;
  if (!view) return;
  try {
    const html = pmFragmentToHtml(view.state.doc);
    onUpdateRef.current?.(block.id, html);
  } catch { /* substrate unavailable mid-tear-down */ }
},
```

### `onRefreshTcSnapshot` — TC-only seam (not substrate)

Existing `onRevisionAction(blockId, html)` in App does `setBlockHtml + setBlocks + tc.applyResolveAtBlock`. The del-popup (1f.8) uses it because the popup's mutator works on serialized HTML — substrate write is required.

For FloatingToolbar inline accept/reject in PM mode, PM `view.dispatch(tr)` already wrote the substrate via `ySyncPlugin`. Calling `onRevisionAction` would:
- Open a second `'local-publish'`-origin Yjs transaction with redundant ops (caught by y-prosemirror diff-and-merge in most cases, but still mounted).
- Enter the Yjs UndoManager via the `'local-publish'` filter (per CLAUDE.md invariant 2) — phantom Ctrl+Z frame.
- Broadcast the same content to peers a second time.

New App-side handler:
```js
const handleRefreshTcSnapshot = useCallback((blockId, html) => {
  setBlocks(prev => prev.map(b => b.id === blockId ? { ...b, html } : b));
  setTcState(s => tc.applyResolveAtBlock(s, blockId, html));
  // Deliberately NO setBlockHtml — PM dispatch already wrote substrate.
}, [setBlocks]);
```

Wired as new prop `onRefreshTcSnapshot` on FloatingToolbar. The del-popup path in `PmEditableBlock.jsx` is unchanged.

### `App.jsx` — minimal changes

1. New handler `handleRefreshTcSnapshot` (above).
2. Pass `onRefreshTcSnapshot={handleRefreshTcSnapshot}` to `<FloatingToolbar />`.
3. Pass `identity={identity}` to `<FloatingToolbar />` for `authorId` on revision marks.

No changes to `useCollabSession`, `track-changes.js`, `pm-schema.js`, `pmdoc-html.js`, `collab.js`.

## Risks

1. **Playwright `dispatchEvent('mousedown')` bypasses PM's domObserver.** `pmSetSelection` upfront mitigates. If a test still fails because the toolbar's own mousedown handler doesn't fire under `dispatchEvent` (it might be a `.click()` issue, not selection), fall back to `page.locator(button).click()` which routes through the browser's native pointer pipeline.
2. **`onRefreshTcSnapshot` deviates from the del-popup seam.** Reviewers may push back on having two TC-refresh paths. Justification: del-popup mutates serialized HTML (must write substrate); FloatingToolbar in PM mode dispatches a PM transaction (substrate already written). Documenting in CLAUDE.md is sufficient.
3. **Comment button invisibility in PM mode.** Documented; pre-existing; #64 blocks the fix. Not introducing a new regression.
4. **The DEV-only `__overrideFlush` seam.** Adds a test-only API surface. Justified by E1's negative-control requirement (review item E2 blocker). Gated by `import.meta.env.DEV` so it does not ship in production builds.
